# 网页认证 IP 防护

公开 `/api/v1/auth` 路由默认启用以下防护；管理员建号和业务 API 不使用注册额度。

| 行为 | 默认策略 |
| --- | --- |
| 邮箱或 OAuth 新建账号 | 同一 IP 累计最多 2 个，跨实例共用 PostgreSQL 额度 |
| 网页密码登录、OAuth 绑定登录、2FA、passkey finish | 同一 IP 首次失败起 15 分钟内累计 10 次失败后，封禁认证入口 1 小时 |
| 封禁期间 | 认证路由返回 HTTP 429 和 `Retry-After`，不执行后续认证；被拦截请求不延长封禁 |
| Redis 不可用 / 无法解析客户端 IP | 认证入口拒绝请求，返回 HTTP 429，避免失去防护后继续尝试 |

登录失败累计包含上述登录入口返回的 HTTP 400/401/403（包括错误密码、验证码或格式错误）；429 限流与 5xx 服务故障不累计。不同登录方式共用失败计数；成功登录不清空失败历史。第 10 次失败保留原有错误响应，其后的请求返回 429；已经放行的并发请求可能继续完成。

注册额度在所有公开认证请求的上下文中标记，在统一用户仓储中以原子 UPSERT 扣减，与用户写入及外层邀请码事务一同提交或回滚。不因重启或清理 Redis 丢失。删除账号不退额度，防止删号重领；账号创建已经提交后的后续 OAuth 绑定补偿删除也不退额度。达到上限返回 HTTP 403、`reason=REGISTRATION_IP_LIMIT`。已有账号登录不扣额度。

## 升级与可信代理

迁移 `285_registration_ip_quotas.sql` 自动创建独立额度表，不修改历史用户。历史账号没有可靠的注册 IP，不能从最近登录 IP 推断，因此不追溯额度，从升级后开始累计。

这两项防护使用 `GetTrustedClientIP`，只通过 Gin 的 `server.trusted_proxies` 信任链（或已有验证的转发 IP）获取地址，忽略兼容模式对原始 `CF-Connecting-IP`、`X-Real-IP`、`X-Forwarded-For` 的直接信任。IPv4、IPv4-mapped IPv6 和 IPv6 文本变体先规范化再计算 SHA-256。

反向代理部署必须在 `server.trusted_proxies` 中列出实际反代地址/网段，并让反代覆盖客户端 IP 头；不要信任任意来源或允许客户端绕过反代访问源站。配置错误可能把所有用户算到同一代理 IP。共享公网出口下多个用户共用两个注册名额，管理员可通过后台代建账号。IPv6 按单个地址计数，不按 /64 合并；换 IP 的分布式攻击仍需要验证码、邀请制或边缘防护。

## 状态与解除封禁

新表仅保存规范化 IP 的 SHA-256 和累计账号数，无原始 IP、邮箱或密码。哈希用于避免直接记录 IP，并非匿名化承诺。此防护不新增用户凭据日志，也不内置任何事件中的真实 IP。

Redis 键为 `auth_abuse:{<IP SHA-256>}:failures` 和 `auth_abuse:{<IP SHA-256>}:banned`，分别带 15 分钟和 1 小时 TTL。正常到期自动解除。管理员确认误封时，可计算目标 IP 的规范化哈希，仅删除这两个对应键；不要清空 Redis。Redis 状态被清理或 Redis 无持久化重启会清除临时封禁，因此仍应保留边缘/fail2ban 防护。

回滚二进制不会删除额度表，可保留以便重新升级；旧二进制不会继续统计。跨新旧版本灰度期间，旧实例建号不受新额度约束，因此应一并升级公开认证实例。此次变更不包含 SSH、系统防火墙、发布或生产部署操作。
